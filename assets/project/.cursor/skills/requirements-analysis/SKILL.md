# Requirements Analysis

## Inputs
A feature idea, bug report, product request or existing specification.

## Procedure
1. Identify user, problem, desired outcome and business constraints.
2. Ask one question at a time only when a missing answer materially affects the design.
3. Define primary and secondary user journeys.
4. Specify functional behavior, permissions, validation and state transitions.
5. Capture non-functional needs: security, privacy, performance, accessibility, reliability and observability.
6. Enumerate empty, invalid, boundary, failure, retry, concurrency and recovery cases.
7. Define measurable acceptance criteria.
8. Separate requirements, assumptions, decisions and non-goals.
9. Check for conflicts with existing behavior and contracts.

## Guardrails
Do not silently invent product policy, pricing, retention, permissions or legal requirements. Mark unknowns explicitly.

## Deliverable
A concise requirements brief, user flows, acceptance criteria, edge-case matrix, open questions and non-goals. Do not code unless asked.
